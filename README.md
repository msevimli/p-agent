# p-agent (plife) — Multi-Channel Self-Hosted AI Agent Platform

A self-hosted, multi-modal AI agent platform: a **web dashboard**, a
**Telegram bot**, and a **terminal CLI (`pagent`)** all drive the same agentic
pipeline — tool calling (shell, files, library, skills, automations), streaming
responses, persistent sessions, and a built-in automations scheduler — over
local llama.cpp models *or* remote OpenAI-compatible providers (OpenRouter).

```
 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │  Web UI      │   │  Telegram    │   │  pagent CLI  │
 │  :8888       │   │  long-poll   │   │  terminal    │
 └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
        └──────────────────┼──────────────────┘
                   ┌───────▼────────┐
                   │  /api/chat     │  agentic tool loop
                   │  (single      │  queue + tools + sessions
                   │  pipeline)     │
                   └───────┬────────┘
                    llama.cpp │ OpenRouter (OpenAI-compatible)
```

## Quick start

```bash
git clone https://github.com/msevimli/p-agent.git && cd p-agent
npm install
cp .env-example .env        # add LLAMA_API_KEY for remote models
npm start                   # → web dashboard at http://localhost:8888
```

The chat pipeline needs an active model. Two options:

- **Local llama.cpp** — run `llama-server -m <model>.gguf --port 8080` and use
  the built-in local models (Gemma 2, Qwen2.5 Coder, Mistral 7B, Llama 3.2 3B…).
- **Remote OpenRouter** — set `LLAMA_API_KEY=<key>` in `.env`, then pick a
  remote model in **Tools → Models** (deepseek, qwen, nemotron, ling…). Keys
  are stored only in `.env` (per-model keys: `LLAMA_API_KEY_<MODEL_ID>`),
  never duplicated into state files.

> The frontend loads Tailwind, marked and highlight.js from CDNs — an internet
> connection is needed for UI styling on first load.

## Model lifecycle & cold-start controls

The header shows a live **model status badge** for the active model — green
**ready**, amber spinner **loading** (warm-up or prompt prefill / cold start),
gray **unloaded**, red **error** — with an approximate memory footprint in the
tooltip. Clicking it opens a dropdown with **Warm-up** (background pre-load so
the first prompt responds instantly) and **Eject** (free the weights from
memory) plus a shortcut to the Models panel. The badge polls
`GET /api/models/status` every 15s and refreshes immediately after sends,
warm-ups and ejects.

- Lifecycle states are derived per model endpoint from `/health`, `/v1/models`
  and `/slots` (see `services/modelLifecycle.js`); a 2-probe debounce absorbs
  llama.cpp's task "tombstones" (a finished task leaves `id_task` set, which
  would otherwise pin the badge on "busy" forever).

### Load & Eject per model (Models panel)

Each local model card has **Load** / **Eject** buttons — no terminal needed.
Loading derives a systemd *user unit* `~/.config/systemd/user/llama-<id>.service`
from the model's **launch template** (Tools → Models → Templates tab:
`llama-server` flags, `<model-file>` placeholder; the **Default** template
`-fa 1 --jinja -c 16384 …` is built in and editable). The unit ALWAYS binds
`--host 0.0.0.0` (appended last so llama.cpp's last-wins parsing keeps it
authoritative — external tools like llama-ui must reach the server; if the
host is network-exposed, put `--api-key` in your template or add a firewall
rule). Units generated by p-agent carry a marker in their Description and are
re-rendered on the next Load when the template changed; hand-crafted units
(no marker, e.g. a tuned `llama-router.service`) are preserved untouched.

- `POST /api/models/:id/load` — spawn/verify the model's server (idempotent:
  `{ok:true, already:true}` when online; **409** when the port already serves a
  different model — the occupant must be ejected or the entry re-pointed to a
  free port first).
- `POST /api/models/:id/eject` — terminate and free RAM immediately
  (live-verified: 14B eject freed ~9.3 GB in one call). Refuses (409) when the
  port serves a different model and this model's own unit is not active —
  ejecting never touches a foreign server.
- **Identity-scoped status** — several registry entries may share one port
  (e.g. six .gguf entries on 8081). Status verifies the served identity
  (`/v1/models` alias ids + `/props` model_path against the entry's GGUF
  name), so only the genuinely loaded model reports **online** with an Eject
  button; same-port siblings report **conflict** ("port busy") with Load.
- **Warm-on-activate** — activating a model also queues a background warm-up,
  so switching models does not cost a cold first turn.
- **Warm-up** (`POST /api/models/warmup`) runs a `max_tokens=1` completion
  containing ONLY the static prompt prefix (short system prompt + ALL tools,
  `cache_prompt: true`) through the same FIFO request queue as chat — never
  two concurrent connections into a single-slot llama.cpp. Local endpoints
  only. The agent also warms up on startup (`AUTO_WARMUP=false` to disable).
  After a warm-up, the first real message starts from a KV-cache hit (the
  usage badge shows it: "6.1k tok (5.9k cached) · 12.1/2.6 tok/s").
- **Cloud-vs-local payload filtering** — llama.cpp-only sampling/cache params
  (`repeat_penalty`, `repeat_last_n`, `cache_prompt`) are stripped from chat
  payloads routed to cloud/OpenAI-compatible endpoints (Nvidia NIM rejects
  them with HTTP 400 "Unsupported parameter(s)"); local loopback targets keep
  them (KV cache reuse stays on). The Generation popover's **Advanced local
  params** toggle disables them on local targets too and auto-disables when
  the active model is cloud-hosted. A one-shot retry with the minimal
  OpenAI-safe payload covers any provider rejection that slips through.
- **Prompt caching:** the system prompt and the full 16-tool array are
  byte-stable (static text, tools sorted by name, identical serialization),
  `cache_prompt: true` is set on every request, and dynamic content is never
  injected before the history — so llama.cpp re-evaluates only the new user
  message + last reply on subsequent turns of a conversation. Every `[llm]`
  log line carries `prefix=<hash>` of the serialized prefix; a runtime
  change logs a warning.
- **Tool output limits & history compaction:** one tool result is capped at
  `TOOL_OUTPUT_MAX_CHARS` (4000, head+tail with a truncation marker applied
  once at insertion — run_shell keeps mostly the tail); read_file supports
  line offset/limit and caps at READ_FILE_MAX_CHARS; list_files caps entries
  and reports the omitted count. Compaction is a deterministic REPLAY of the
  conversation with the fixed chars/3.4 estimator (never the per-request
  usage.prompt_tokens calibration, which only feeds logs/UI): a compaction
  event fires only when the running estimate crosses 75% of the context
  budget (n_ctx − prefix − 1024 reserve − 5% margin) and brings the state to
  50% — oldest tool results stubbed, then oldest complete turns dropped,
  always keeping the last 3 user turns. The cut is sticky, so between
  events every request reproduces the byte-identical compacted prefix and
  only the new messages re-evaluate; `workspaces/scripts/compaction-stability-sim.js`
  proves this (prompt tokens, common prefix, re-evaluated tokens per turn,
  ±10% calibration-invariance). Compaction events and estimated re-prefill
  time (tokens after the first changed position ÷ measured prompt speed)
  are logged (`[ctx] compact(...)`). A context-exceeded error triggers one
  compact-and-retry, then a clear error.
- **Misformatted tool calls (tolerant fallback + guard retry):** some llama.cpp
  builds leave a correctly-shaped call wrapped in an XML/JSON tag (`<tools>`
  — Qwen2.5-Coder —, `<tool_call>`, `<tool_calls>`, `<function_call>`,
  `<function-calls>`) or a fenced JSON block in the raw assistant content with
  `tool_calls` empty. A strict parser (`services/toolCallParser.js`) converts
  exactly this shape — only the assistant's own content, tool name must exactly
  match a registered tool, and both `{name, arguments}` (OpenAI/Qwen) and
  `{tool, args}` (plife contract) key shapes are accepted; arguments must be
  valid JSON, missing → `{}`. Several `<tools>` blocks (or one block holding an
  array) in a single completion all execute in emission order; anything invalid
  stays plain text (never executes). The tag text never reaches the stored
  history or the UI, and each use is logged (`[tool-fallback] variant=…`). If a
  reply still has no call but contains a shell block / curl / wget on a
  live-data request, the agent retries ONCE with the stable instruction and
  `tool_choice:"required"` for that single completion (config
  `GUARD_RETRY_TOOL_CHOICE`, default on). Genuine plain-text replies log the
  finish reason and content head (`[llm-no-call]`). Every executed tool call
  logs one line with real exit code, duration and the first 200 chars of
  command / stdout / stderr, JSON-escaped
  (`[tool] name=run_shell exit=0 dur=1.2s cmd="…" out="…" err="…"`). Tests:
  `workspaces/scripts/tool-call-fallback-tests.js` (mocked, no server).
- **Eject** (`POST /api/models/:id/eject` or the header dropdown) is
  capability-tiered: native weight unload via llama.cpp's model-router API
  (`POST /models/unload`) when the build supports it → an active-model busy
  guard (409 — never kill a request mid-flight) → **systemd unit-stop** for
  p-agent-managed units (process terminated, memory freed immediately) → an
  honest `{ok:true, unloaded:false, degraded:true}` response for hand-run
  servers that can neither unload nor stop — never a claim that weights were
  freed when they weren't.
- Memory reporting is approximate: weights ≈ GGUF file size on disk plus the
  KV context capacity reported by `/slots`.

## Reasoning controller & visibility (Off → High)

Models that expose an internal thinking trace (Gemma 4, DeepSeek-R1-style
distills, Qwen-Reasoning, OpenRouter reasoning models) stream it live:
`reasoning_content` deltas and ` thinking... ` / `.../thinking` tags are
extracted per tool-loop round and relayed as structured SSE
(`type:"reasoning"`) separate from the answer text. Each message renders a
collapsible **Thinking…** panel above the answer — pulsing while streaming,
auto-collapsing the moment the final answer starts, expandable any time.

**Multi-level controller** (brain-icon button in the compose toolbar): shows
the current level as a badge and opens a dropdown with five levels:

| Level | Backend mapping |
|-------|-----------------|
| **Off** | `reasoning_effort: "none"` (natively disables thinking on this llama.cpp build) + all panels hidden, live and history |
| **Default** | no reasoning params — the provider/model default behavior |
| **Low / Medium / High** | `reasoning_effort: "low"\|"medium"\|"high"`, plus (loopback endpoints only) `thinking: {type:"enabled", budget_tokens: 1024/4096/16384}` — llama.cpp maps it to `thinking_budget_tokens` |

The level is persisted (`localStorage` `pagent.reasoningLevel`; the legacy
binary `pagent.showReasoning='0'` migrates to `off`) and rides every
`/api/chat` request as `reasoningLevel`. `buildChatPayload` injects the
parameters into the completion payload ONLY — never into the prompt — so the
KV-cache prefix stays byte-identical across levels (a warm cache stays warm;
the only exception is caps-style templates that bake effort into their own
rendering: one-time prefill after switching, then stable). Cloud endpoints
never receive the Anthropic-style `thinking` field, and unknown levels are
dropped rather than echoed to strict providers.

## System prompt management (Tools → System)

The **Tools → System** panel shows the exact system prompt that is sent to the
model on every chat turn — the generated template (base instructions + FILE
TOOL PAYLOADS + automations guidance) or your override — in a full-size mono
editor:

- **Save Changes** (`POST /api/system/prompt`) persists the edited text to
  `data/system-prompt.txt`; it then REPLACES the built-in template
  byte-for-byte on every turn (tool path and tool-less path alike) until
  **Reset to Default** (`DELETE /api/system/prompt`) clears it.
- Because the override changes the prompt, the KV-cache prefix changes with
  it — the first turn after saving/resetting is a one-time prefill, then the
  new prefix caches normally (and chunked prefix caching keeps the old one
  resident in practice).
- `GET /api/system/prompt` always returns the ACTIVE prompt (override or
  template), so the editor shows ground truth; a "custom" badge marks the
  override state.

## Automations (Tools → Automations)

Scheduled jobs (interval or cron) that run shell scripts or agent prompts at
a cadence:

- Every card has a **per-automation switch** — off means the scheduler skips
  it (`nextRunAt` is cleared; `POST /api/automations/:id/toggle` with
  `{enabled: true|false}`). Manual **Run now** still works for disabled
  automations.
- The panel top has a **"Pause all automations" master switch** — one click
  stops the whole scheduler (`POST /api/automations/pause` with
  `{paused: true|false}`, `GET /api/automations` reports `paused` + a nulled
  `nextRunAt` per rule). While paused, per-item switches are inert and no job
  fires on schedule, but manual **Run now** remains available; unpausing
  restores the schedule only for enabled automations.
- State (including the paused flag) persists in `data/automations-state.json`.
- The agent itself can manage these states with the automation tools:
  `set_automation_enabled {id, enabled}` (one rule) and
  `set_automations_paused {paused}` (whole scheduler) — registered alongside
  create/list/run/delete, auto-included when the conversation mentions
  automation/pause/disable keywords, and documented in the system prompt
  (template and any active override).

## System resource monitor (header)

Two compact circular gauges in the header (left of the model status badge)
show live **RAM** (blue) and **CPU** (violet) usage with the percentage
inside the ring: `GET /api/system/metrics` (Node `os` module, no
dependencies). Warnings at ≥85% and critical at ≥95% tint the ring amber/red.
Tooltips carry the raw numbers (GB used / total, core count, load average,
uptime). The widget polls every 5s and sweeps smoothly between samples.

- **RAM** is kernel-accurate and **container-aware**: inside a Docker
  container (`/.dockerenv` / cgroup markers) usage and limit come from the
  process cgroup — cgroup v2 `memory.current`/`memory.max` or cgroup v1
  `memory.usage_in_bytes`/`memory.limit_in_bytes` — so the header matches
  `docker stats` (used = cgroup usage; total = the container's limit, or
  host memory when the cgroup is unlimited, mirroring docker-stats LIMIT).
  Bare metal falls back to `/proc/meminfo` with the procps `kb_main_used`
  formula (buffers + page cache count as used) plus `percentAvail`
  (`MemTotal − MemAvailable`, modern `free`'s used column). Beware
  `os.freemem()` on Linux ≈ MemAvailable (reclaimable cache included), so a
  plain `totalmem − freemem` understates the naive ratio whenever cache is
  large — and on WSL2 it can disagree with Windows Task Manager's vmmem
  accounting, which counts the VM's held cache too.
- **CPU** is container-aware like RAM: inside a container the delta comes
  from the cgroup's own counters — `cpuacct.usage` (cgroup v1, ns) or
  `cpu.stat usage_usec` (cgroup v2) — with the percentage expressed against
  the allocated quota (`cpu.max` / `cpu.cfs_quota_us`), or the host core
  count when the quota is unlimited. Bare metal keeps the `os.cpus().times`
  tick-delta method. In both cases the very first sample has no baseline
  and falls back to a loadavg-based estimate for one tick.

## Daemon lifecycle management (`pagent.sh`)

The root-level `pagent.sh` is the unified management script — instead of
tracking PIDs or juggling `nohup` by hand, use it for the whole process
lifecycle. State lives in `data/pagent.pid` (PID file) and
`data/pagent.log` (boot/run logs) — both gitignored.

```bash
./pagent.sh --start
```

Spins up the backend daemon **in the background** (agent loopback, Telegram
poller, and automations scheduler all boot with `server.js`). Before
launching it:

- verifies `node` and `node_modules` (hints at `npm install` if missing),
- creates `.env` from `.env-example` when absent (warned),
- refuses/warns on double starts — it checks the PID file first, then scans
  for a `node server.js` process and probes port `8888`,
- writes the PID to `data/pagent.pid` and waits until `/api/health`
  responds (up to 30s); on failure it prints the log tail and cleans up.

```bash
./pagent.sh --status
```

Reports whether the daemon is running: PID, uptime (`ps etimes`), port, and a
live `/api/health` check. It also distinguishes tracked processes (started
via the script) from untracked ones, detects stale PID files, and exits
non-zero when the service is down.

```bash
./pagent.sh --stop
```

Terminates the daemon gracefully: sends SIGTERM (the server stops its
Telegram poller and schedulers cleanly), waits up to 10s, escalates to
SIGKILL if needed, removes `data/pagent.pid`, and verifies the port is
released. Servers started outside the script are detected by process/port
scan and stopped with a warning.

Notes: `PORT=<other> ./pagent.sh --start` runs on a different port;
`NO_COLOR=1` (or a pipe) disables colored output.

### Interactive REPL

```bash
pagent                      # opens a chat REPL
You> what files are in the library?
⚙ Listing Library files
…streamed answer…
You> /help                  # commands: /new /attach /model /exit
```

REPL commands: `/help`, `/exit`, `/quit`, `/new [name]` (fresh session),
`/attach <name|id>` (attach a Library file to the next message), `/model <id>`.
`Ctrl+C` aborts the in-flight generation; pressing again exits.

### One-shot prompts

```bash
pagent chat "fetch the current Solana price"
pagent "create a backup automation for every 6 hours"
```

### Management subcommands

```bash
pagent sessions             # list browser + Telegram + CLI sessions
pagent models               # list models, * = active
pagent models deepseek      # switch the active model
pagent channels             # Telegram bot status (token, whitelist, polling)
pagent channels on|off      # enable/disable the Telegram channel
pagent config               # effective configuration (secrets masked)
pagent config set LLAMA_MAX_TOKENS=8192   # edit .env values
```

Add `--json` to `sessions`/`models`/`channels` for machine-readable output.
Chat and write commands talk to the local server (`PAGENT_BASE_URL` overrides
`http://127.0.0.1:8888`); read-only commands fall back to the local `data/`
state files when the server is down.

## Telegram channel

1. Create a bot with [@BotFather](https://t.me/BotFather) and copy the token.
2. Open **Tools → Channels**, paste the token, **Save token** (written to
   `.env` as `TELEGRAM_BOT_TOKEN`, never into state files).
3. Message your bot once, reply to `/id`, and add the returned chat id to the
   **whitelist** (comma-separated) — or set `TELEGRAM_ADMIN_CHAT_ID` in `.env`,
   which is always allowed and cannot be removed from the UI.
4. Flip the toggle. The bot long-polls (50s) without any extra dependency.

In-chat commands: `/id`, `/status`, `/help`. Authorized chats reach the **same
agent pipeline** as the web/CLI — tools, Library attachments, automations, and
the request queue included. Conversations persist as normal dashboard sessions
(`tg-<chat_id>`) with full history replay, so the bot remembers context and
you can read the whole exchange in the sidebar. Unauthorized chats get one
short refusal and never trigger the agent.

## Resilience & smart tool handling

- **Agentic tool loop with dual call formats** — native OpenAI `tool_calls`
  (remote providers) *and* a tolerant JSON-block contract
  (`{"tool": "...", "args": {...}}`, fenced or bare) for Content-only
  llama.cpp builds; calls are schema-validated before execution (missing or
  placeholder args are rejected with corrective feedback, never run).
- **No duplicate suppression** — every tool call executes exactly as
  emitted, however often the same (tool, args) already ran this request:
  re-running a grep or re-reading a file after an edit returns fresh state
  (identical repeats are never skipped; there is no per-request ledger).
  `run_shell` runs back-to-back repeats verbatim too.
- **Tool argument normalization** — small models routinely emit the right
  value under the wrong key or as a bare unkeyed string. Before validation,
  `file`/`filepath`/`file_path`/`filename`/`src`/`target` (and bare strings)
  map to `path` for the file tools, and `cmd`/`exec`/`script`/`c`/`shell_command`
  (and bare strings) map to `command` for `run_shell` — the call EXECUTES
  instead of entering a reject-repeat loop. Status labels resolve the same
  aliases, so the activity feed shows the real command/path.
- **Rejection feedback & safety nets** — a rejected call names the
  missing key AND the expected shape (`Expected format: {"path": …}` /
  `{"command": "your_shell_command_here"}`; placeholder text like
  `?` is also refused), and the model gets the corrective error to retry
  with complete arguments. The tool loop has **no round ceiling and no
  repetition detection** — identical repeats (re-running a grep or
  re-reading a file after an edit) return fresh state and are never
  skipped as "duplicates", and deep multi-step investigations run until
  the model answers naturally, the client stops the turn, or the
  repeated-invalid-call freeze trips (the SAME broken emission 3× makes
  zero progress, so it forces the final answer instead of spinning).
  Conversation-based path recovery exists ONLY for
  read_file/write_file/edit_file — never inferred for run_shell, delete_file
  or anything else.
- **Persistent tool-run history (session replay)** — every executed
  tool step is streamed as a structured `type:"tool"` SSE
  event (tool name, bounded arguments, outcome preview, exit code,
  timestamp) and persisted by the frontend into the session message store
  as `role:"tool"` records; on refresh/session switch they reload as
  collapsible cards (✓ ok / ⏭ skipped / ✗ failed, expandable args +
  output/error). Tool records are excluded from the model-bound
  `apiMessages` (server-side history keeps its own tool glue) and bounded
  (args ≤ 600 chars, output ≤ 400, error ≤ 240) so sessions stay light.
- **Malformed-JSON auto-repair in tool calls** — if a cloud model emits
  tool-call arguments that fail strict `JSON.parse` (unescaped quotes or
  newlines inside nested inline commands like `node -e "…"`, single-quoted
  strings, unquoted keys, trailing commas, smart quotes, `None`/`True`/
  `False`, truncation), `services/jsonRepair.js` repairs them through a
  parse-verified cascade: every repaired candidate must `JSON.parse` AND
  pass a key-cleanliness + structural-boundary gate (an escaped quote that
  would swallow a `,"key":` boundary is rejected — the repair never merges
  two key/value pairs into one mangled string), so no corrupted shape is
  ever executed. Valid JSON is never touched (fast path); unrepairable
  input keeps the strict corrective-round flow. Embedded script code in
  `write_file`/`write_skill` values (`data["solana"]["usd"]`, `f"{x}"`,
  multi-file `files` maps) is a dedicated step: it locates every
  `"key": "` value span and escapes all non-delimiter quotes between the
  opening and the structural closing quote (`]`-ambiguity, array-literal
  and dict-literal false closers are tried as separate candidates, all
  parse-verified; a candidate whose escaped quote sits at a `,"key":`
  boundary is dropped). The system prompt and tool schemas instruct models
  to escape internal quotes (`data[\"solana\"]`) or write one file per
  `write_file` call instead of deep unescaped code nests. Wired into every parse
  site: `toolLoop.safeParseArgs` (native `tool_calls`), `extractToolCalls`,
  `parseCallPayloads`, `normalizeCallObject` and `toolCallParser` (tilde
  tags/fences + double-encoded arguments).
- **Shell guidance: script files over inline one-liners** — the `run_shell`
  tool schema, `write_file`'s schema and the system guidance (template +
  active override) tell the model to keep commands short and single-line,
  and to write multi-line or quote-heavy logic to a script file
  (write_file → `workspaces/scripts/x.js`, then `node scripts/x.js` from the workspace shell / `bash scripts/x.sh`) instead of
  fragile nested-quote inline `node -e`/`python3 -c` one-liners whose JSON
  escapes get corrupted mid-task. This prevents the corruption class at
  the source, the repair module catches what still slips through.
- **Session re-attachment & background turn sync** — running turns belong
  to their SESSION, not the current view: the SSE reader keeps consuming
  into a per-session buffer (`state.activeStreams`) while you browse other
  sessions, so switching back re-attaches statuses, partial text, reasoning
  and tool cards to fresh DOM and resumes the timer/stop button exactly
  where they were. The backend mirrors every active turn in a registry
  (`GET /api/chat/state/:sessionId`, keyed by the `sessionId` the client
  sends with each chat request; records outlive the turn by 90 s), so a
  stream lost to a hard refresh is polled and folded back into the session.
  Tool records and final answers always persist into the stream's OWN
  session — a background turn can never write into the session you are
  viewing.
- **Sidebar processing indicator** — sessions with an active turn show a
  pulsing amber dot (`.session-processing-indicator`, glow animation,
  reduced-motion aware) next to their title; it clears when the turn ends
  or is stopped.
- **Never stalls on a broken model** — if the active model returns an empty
  stream when tool calling is enabled (some providers do), the request is
  automatically re-run without the tools array and still answers, with a
  status event explaining the fallback.
- **Transient-provider handling** — the FIFO request queue retries network
  gremlins, empty streams, OpenRouter 402 (in-flight budget) and 429
  rate-limits with escalating backoff (8s for throttling-class errors).
- **Length-cap continuation** — outputs cut by `max_tokens` are completed in
  up to 8 continuation rounds instead of truncated mid-code (or mid-JSON call).
- **Automation enforcement** — asking for a recurring task forces the model to
  call `create_automation` instead of explaining how; the server can also
  create it directly from your wording when the model refuses.

## Agent workspace isolation (workspaces/)
Agent file tools (`read_file`, `write_file`, `edit_file`, `delete_file`, `list_files`), `run_shell` and the workspace `MEMORY.md` default to the **agent workspace** — `workspaces/` inside the project root — so generated scripts, reports and dynamic files never clutter the project root. Zone rule (two-zone resolution, `services/agentPaths.js`):
- BARE relative paths (`scripts/foo.py`) → `workspaces/scripts/foo.py`
- `..` / `../x` → the **project root** (e.g. `../routes/fs.js`) — one level up from the workspace
- `../../x` or absolute paths → rejected (the hard sandbox is still `workRoot` via `resolveWithin`; zoning only picks where inside the project a bare path lands)
- `list_files` with no path lists the workspace; `list_files ..` lists the project root; `run_shell` starts in the workspace (`cd ..` reaches the root)
Automation scripts keep the project root as cwd (user scripts reference e.g. `workspaces/scripts/date_time_script.py`); agent-written scripts referenced by automations use `workspaces/...` paths. The File Explorer browses the whole project root (breadcrumb `Root` / `Root > workspace`) with Root/Workspace quick-toggle buttons.

Since 2026-10-28 the workspace is the **physical home** of the former root `scripts/` (repo test harnesses + user runtime scripts, `git mv`-tracked) and `skills/` (agent-managed skills + the trading-dashboard app). Test suites are invoked as `node workspaces/scripts/<suite>.js`; the one-off migration script is `workspaces/scripts/migrate-workspace.js`. `config.workspaceDir` (env `WORKSPACE_DIR`) defaults to `<workRoot>/workspaces/` and `config.skillsRoot` points the skills store at `<workspaceDir>/skills`. The trading dashboard runs as a systemd USER unit (`trading-dashboard.service`, workdir `workspaces/skills/trading-dashboard/`, port 3005) — `systemctl --user status|restart trading-dashboard`.

## Semantic memory (two tiers)

1. **Workspace memory** — `MEMORY.md` at the workspace root: project facts,
   decisions and conventions, injected into every request while the file
   exists. Manage it with the `update_workspace_memory` tool
   (read/append/overwrite, capped at 48 KiB — it rides inside every prompt)
   or the Memory tab in the sidebar.
2. **Global memory** — long-term user facts (preferences, style, personal
   instructions) embedded locally and retrieved semantically (top-k, default
   3) per turn, injected as a `<global_user_memory>` block. Store is
   `data/vector-memory.db` (Node's built-in SQLite; JS cosine search —
   swap-ready for a SQLite vector extension). Facts are added by the
   `manage_global_memory` tool, automatically from conversation, or the
   Memory tab.

Cache-safe by design: the system prompt carries only **static** guidance;
the dynamic memory blocks are appended as the LAST message of each request
(never into history), so the llama.cpp KV prefix stays byte-stable and only
the short tail is re-evaluated. Embedder chain (`VECTOR_MEMORY_EMBEDDER`):
`xenova` (all-MiniLM-L6-v2, real semantics) → `ollama` → `hash`
(deterministic n-gram fallback, no deps); `auto` picks the first available.
